# AGENTS.md — Lumen Design System

> Universal agent rules for any AI coding agent working in this repo (Cursor, Claude Code, Codex, Devin, Copilot, etc.). Read this before doing anything. If you are Claude, also read [CLAUDE.md](./CLAUDE.md). If your tool has its own rules format (Cursor's `.cursor/rules/`, Warp's `.warp/`), they mirror this file.

## What this repo is

Lumen is the source of truth for Warp's UI. It contains design tokens (DTCG JSON), component contracts (Markdown + JSON sidecars), and platform consumption guides. It does NOT contain shipped product code — product code lives in consumer repos and pulls Lumen via shadcn registry / Swift Package / Compose module / etc.

Children are ALWAYS in the DOM (SSR ships full content, Cmd+F works, screen readers walk, JS-disabled works); the browser's layout engine handles paint-deferral at the CSS level — equivalent lazy-paint behavior to the IntersectionObserver, just at a different layer. The `eager` prop is preserved (no content-visibility on above-the-fold). The `rootMargin` prop is removed (the browser's native near-viewport heuristic handles it). **SSR HTML on /library: 91,854 → 564,618 bytes (+6.1×)** — full content now in initial HTML. All 7 sampled lazy-section strings now appear in SSR (`Auto-quote`, `Contract rate`, `Email me when`, `Get rates`, `Pick or type`, `Save draft`, `Tab bar`) — pre-R12 none were. Browser support: Chrome/Edge 85+ (2020), Safari 18+ (Sep 2024), Firefox 125+ (Apr 2024). Older browsers fall back to full eager rendering — paying the layout cost but still seeing content (graceful). **R12 methodology contribution to the audit-cycle ladder:** *a doc that "describes the intent" and a runtime CSS that "implements the intent" can drift silently — the only way to know is to walk every route with eyes on the rendered pixels AND probe the live token values via `getComputedStyle(documentElement).getPropertyValue(...)`. ## Hard rules (MUST follow, no exceptions)

1. **Never invent tokens.** If you need a value not in `01-tokens/semantic/`, the answer is to ADD a semantic alias (with a PR + ADR), NOT to import a primitive directly or hardcode a value. Hardcoding hex codes, pixel sizes, or font stacks anywhere in component code is a violation.

2. **Always reference SEMANTIC tokens, never primitives.** `color.surface.default`, NOT `color.warm.50`. `space.4`, NOT `dimension.4`. `radius.card.default`, NOT `radius.lg`. Lint enforces this.

3. **Every component contract MUST validate against `/design-system/02-components/_schema/component.schema.json`.** Missing required fields blocks merge.

4. **Every component MUST ship a `component.json` machine contract before any code template.** The JSON is what LLMs and the MCP server read.

5. **Accessibility is WCAG 2.2 AA, hard floor.** Every interactive element needs visible focus, ≥ 4.5:1 text contrast (≥ 3:1 for large text), keyboard reachability, and an accessible name. AAA where it doesn't add cost.

6. **Use the platform-appropriate code template** from `02-components/{name}/examples/`. Do not invent new patterns when one exists.

7. **The Spring Green accent (`color.accent.500` = `#00FA8A`) plays exactly ONE role**: action / live / success. Never decorative. Never as a second accent. Never on non-action chrome. Adding a second loud color to the system is a brand violation. (v0.11 evolved the accent from lime `#4ade80` to spring green `#00FA8A`; the single-accent discipline is unchanged. See [ADR 0018](_meta/decisions/0018-premium-psychology-recolor.md).)

8. **Honor `prefers-reduced-motion`** in everything that animates. Motion that doesn't respect this fails CI.

9. **Never render white or near-white text on the Spring Green accent surface.** The accent foreground is bound to `color.accent.fg` (`#07120D`, ~14.7:1 AAA on `#00FA8A`). White on spring green is ≈1.4:1 — a WCAG AA fail. Specifically:
   - Do NOT use the shadcn token-bridge utilities (`bg-primary`, `text-primary-foreground`, `bg-card`, `text-card-foreground`, `bg-popover`, `text-popover-foreground`, etc.) in product code. They resolve through `:root` → `--primary-foreground` → `--text-on-accent` → `--lumen-accent-fg`, and Tailwind v4's content scanner has been observed to drop those classes, leaving the element to inherit `--text-primary` (near-white).
   - DO use the v0.9 `.lumen-btn-*` defensive class family (declared in `audit-dashboard/src/app/globals.css`) for any button surface — `.lumen-btn-primary`, `.lumen-btn-secondary`, `.lumen-btn-ghost`, etc. compose statically and ship every time.
   - DO use direct semantic refs for one-off surfaces: `bg-[var(--lumen-accent-4)] text-[var(--lumen-accent-fg)]` (audit-dashboard) or `bg-[var(--color-action-primary-bg-rest)] text-[var(--color-action-primary-fg)]` (canonical via the v0.9 action-surface bridge).
   - Lint rule `lint:no-white-on-accent` enforces both halves automatically. Vendor `audit-dashboard/src/components/ui/*` files are audited by hand; only files listed in the lint's `VENDOR_REWRITTEN` set are exempt from the bridge ban.
   - For the comprehensive button language — sizes, intents, shapes, states, motion, voice — read [`design-system/00-foundations/buttons.md`](design-system/00-foundations/buttons.md). For the rationale read [ADR 0016](_meta/decisions/0016-button-rebuild-v09.md).

10. **Floating UI portals to `document.body` — never render a floating panel as an inline `<div absolute>`** (v0.12.4 — closes ADR 0021 trade-off). Combobox / Select / DropdownMenu / Popover / Tooltip / Calendar dropdowns must escape every ancestor's overflow context. The portal pattern: `createPortal(<div style={{ position: 'fixed', top, left, width, zIndex }} />, document.body)` with `getBoundingClientRect()` re-tracked on scroll (capture phase) + resize. Outside-click dismiss must exempt the portaled list (clicks on options would otherwise close the dropdown before the option handler fires). Inline `<div absolute>` panels look correct in isolation but get clipped by Showcase frames, by `<Card padding="none">` (per ADR 0021 — composes `overflow-hidden`), by glass-strong surfaces, by scroll containers, by any nested flex/grid cell with overflow-clip. Lumen `Switch`, `Tooltip`, `DropdownMenu`, `Popover`, `Dialog` already portal via Radix; v0.12.4 brought the hand-rolled Combobox in line. **Rule:** any new floating panel portals from day one. Don't bet on the consumer never embedding it inside an overflow-clipped ancestor.

11. **Focus rings ride `outline + box-shadow`, never box-shadow alone** (v0.12.4 — closes the v0.12.1 ADR-0021 pagination-focus regression). The global `:focus-visible` rule paints both: `outline: 2px solid var(--lumen-lime-a64); outline-offset: 1px;` PLUS the existing soft `box-shadow: var(--shadow-focus)` glow halo. Box-shadow paints into the element's own painting context which DOES respect ancestor `overflow: hidden` — so a box-shadow-only focus ring on a button inside `<Card padding="none">` is partially clipped, producing visible "underline + vertical bar" fragments at the card's bottom edge. Outline is painted outside the layout box and is structurally immune to ancestor overflow. Modern browsers (Chrome 94+, Firefox 88+, Safari 16.4+) follow `border-radius` for outline when `outline-style` is not `auto`. The `.lumen-btn-primary:focus-visible` rule already declares `outline: none` and overrides via CSS specificity, so the dual-ring brand visual on primary buttons stays as ADR 0016 designed it. **Rule:** when authoring any new `:focus-visible` rule, include `outline` for structural visibility, then layer `box-shadow` for the brand halo. Box-shadow alone fails inside corner-clipped ancestors; outline alone loses the soft brand character.

12. **Position math via inline `style`, not Tailwind arbitrary classes — for thumbs, swipes, handles, calendar nav, anywhere the math is exact and the consumer has to be exactly right** (v0.12.3 cascade-fix to ADRs 0015/0016). Tailwind v4's content scanner has been observed to drop arbitrary `translate-x-[Npx]` / `top-[Npx]` / `left-[Npx]` utilities (intermittent, scanner-dependent — `getComputedStyle` reports `none` despite the className carrying the utility). For thumb / swipe / handle / popover anchor position math, use inline `style={{ left: N }}` (or `style={{ transform: 'translateX(...)' }}`) with a native `transition` declaration (default easing `cubic-bezier(0.2, 0, 0, 1)`). Inline style is scanner-independent; explicit `left` overrides the static-position fallback (no `auto`, no centering surprise on `<button>` elements with default `text-align: center`). The defensive `.lumen-btn-*` and `.lumen-field` class families per ADRs 0015/0016 remain the canonical pattern for component STYLING; rule 12 is specifically about position MATH on toggles, switches, swipe rows, calendar nav, etc. **Rule:** never hand-roll a `translate-x-[Npx]` arbitrary class for position math; either use inline `style.{left,transform}` or build a `.lumen-{primitive}` defensive CSS class system.

13. **Version labels read from `lib/version.ts`, never hardcoded literals** (v0.12.5 — closes the v0.11.13 → v0.12.4 palette-footer drift). Every user-facing version label — header pill, footer line, command-palette footer, foundations brand-voice samples, library / tool / foundations badges, the "End of library — last refreshed" line — must read from [`audit-dashboard/src/lib/version.ts`](audit-dashboard/src/lib/version.ts). Three exports for three contexts: `LUMEN_VERSION` (`"v0.12.5"`) for patch-level chips; `LUMEN_VERSION_MAJOR_MINOR` (`"v0.12"`) for inline mono-cap references that don't need the patch; `LUMEN_VERSION_MAJOR_MINOR_UPPER` (`"V0.12"`) for explicit uppercased brand-voice signals (`SYSTEM V0.12 · LIVE`). The release script (`scripts/release.mjs`) now bumps both the root `VERSION` file and `lib/version.ts` in lockstep; do not let them drift. **Exemptions:** prose descriptions referencing historical versions (e.g. "v0.10 retired JetBrains Mono", "v0.11 retired the warm-cream ramp") stay literal — those are immutable historical annotations. ADR titles, filenames, CSS comments documenting when a rule landed all stay literal. The constant is for *current-version labels rendered in the runtime UI*, not for *prose history*. **Rule:** before rendering a version string in any TSX, import from `@/lib/version`; before adding a new TSX file that ships a version label, audit the existing imports in `dashboard-shell.tsx` / `command-palette.tsx` / `foundations/page.tsx` for the canonical wiring.

14. **`<details>`/`<summary>` accordions suppress the native disclosure marker — always — when composing your own end-of-summary chevron** (v0.12.5 — closes the landing-FAQ Unicode-`▾` mismatch with the commerce + tool lucide-`ChevronDown` pattern). When you write a Lumen accordion that paints its own affordance icon at the END of the summary (the canonical pattern: lucide `ChevronDown size={14}` rotating 180° via `group-open:rotate-180` on the summary), the native browser-default disclosure triangle (▶/▼ in webkit, ▾/▸ in firefox) STILL renders before the summary's text content, which means two arrows compete for affordance — one of them off the brand stroke ladder. The `globals.css` `.lumen-summary` + `summary.list-none` rule suppresses both: `list-style: none` covers modern Chrome / Safari / Firefox via the standard `::marker`; `::-webkit-details-marker { display: none }` covers the pre-2022 webkit fallback. Apply the class on every accordion summary. **Rule:** every new `<summary>` that composes a custom chevron icon gets `class="lumen-summary"` (or the Tailwind utility `list-none` — both trigger the same rule pair). Never let the native marker double up with a custom icon.

15. **The audit-dashboard's bundled Satoshi VF is subset to Latin-1 + design-glyph coverage — re-subset before introducing new content that breaches the keep set** (v0.13.4 — closes R7's LCP soft-spot, ADR 0027). The two woff2 files at `audit-dashboard/src/fonts/Satoshi-Variable.woff2` + `Satoshi-VariableItalic.woff2` ship with **230 codepoints / 303 glyphs** — ASCII + Latin-1 supplement + General Punctuation + Currency Symbols + Letterlike Symbols + basic arrows (↑ ↓ ← → ↔) + used Math operators (− ∞ ≈ ≠ ≤ ≥) + the geometric shapes Satoshi shipped (■ □ ▲ △ ◊ ○ ●) + ✓ +  Apple PUA. **Western European text renders correctly in Satoshi** (français, español, português, Deutsch, italiano, Köln, façade, naïve, über). **Eastern European text (Polish ł, Czech ř, Hungarian ő, Romanian ș, Turkish ğ) falls through to system Arial — visible character-by-character contrast against surrounding Satoshi.** If a future demo needs Eastern European text in Satoshi (or any glyph dropped by the subset), add the required codepoints to the keep set in [`scripts/subset-satoshi.mjs`](scripts/subset-satoshi.mjs), re-run `node scripts/subset-satoshi.mjs`, verify the rebuild via `cd audit-dashboard && pnpm build`, re-run Lighthouse to confirm the LCP budget doesn't regress, and update `.audit-runs/_font-backups/` with the new originals. **Every Lumen-referenced OpenType feature stays preserved** by the subsetter's `--layout-features=*` flag: kern, liga, calt, ss01–ss04, tnum, lnum, sinf, sups, frac, case, locl, salt, dnom, numr. **Variable axis stays preserved**: wght 300–900. The handcoded `Satoshi-Fallback` `@font-face` block in `globals.css` is unchanged and remains the active metric-aligned fallback for Lumen consumers self-hosting Satoshi without next/font (ADR 0010 contract). **Rule:** never assume Satoshi covers Eastern European text in the audit-dashboard — verify against the subset keep set first; never edit the woff2 files outside `scripts/subset-satoshi.mjs` (the codepoint set is declarative + deterministic + auditable in the script source).

16. **The audit-dashboard inlines its CSS via Next.js's `experimental.inlineCss: true` — don't layer a second critical-CSS scheme on top** (v0.13.5 — ADR 0028 R8b). The flag in [`audit-dashboard/next.config.ts`](audit-dashboard/next.config.ts) tells Next.js's build-output transform to replace every prerendered page's `<link rel="stylesheet">` with a `<style data-precedence="next">` block in `<head>`. When generating new Next.js App Router pages or layouts in the audit-dashboard: do NOT hand-roll a parallel critical-CSS inline scheme via `<style dangerouslySetInnerHTML>`, `<link rel="preload" as="style" onload="this.rel='stylesheet'">`, or manual extraction via penthouse / critters / beasties — the build-time transform handles every prerendered page universally and parallel mechanisms produce duplicate CSS bytes in the HTML. The two `@font-face` blocks Lumen depends on (the handcoded `Satoshi-Fallback` from globals.css per ADR 0010 + next/font's auto-generated `satoshi Fallback`) are preserved verbatim in the inlined CSS; CLS contract (ADR 0010) holds because the metric overrides (`size-adjust`, `ascent-override`, `descent-override`) are font-table-derived, not glyph-derived. **For Lumen consumer apps building their own Next.js app:** read ADR 0028's trade-off matrix before enabling — `inlineCss: true` is right for single-visit + atomic-CSS regimes (audit-dashboard, marketing landing pages, status pages); for multi-page apps with high returning-visitor traffic the external CSS cache benefit outweighs the round-trip elimination, and the default (no `inlineCss`) is better. Document the choice in your app's CLAUDE.md / AGENTS.md so future contributors know which path is in effect. **Rule:** never invent a parallel critical-CSS scheme in the audit-dashboard; for consumer apps, make an informed inlineCss call per ADR 0028's matrix and document it.

17. **Lazy-paint the below-the-fold sections on DOM-heavy routes via `<LazyMount>`** (v0.14 — R8c, ADR 0029; v0.14.1 — R12, ADR 0031 — rewrote to content-visibility; **v0.14.2 — R13, ADR 0032 — rewrote to first-paint-only deferral**). When a route renders > 1500 DOM nodes (heuristic: > 30 primitive showcases, > 60 cards, or measured DOM-size > 1500 per Lighthouse), wrap the below-the-fold `<Section>` blocks in [`<LazyMount>`](audit-dashboard/src/components/lazy-mount.tsx). **R13 implementation:** the component is `"use client"`. SSR + initial render apply `<div style={{ contentVisibility: "auto", containIntrinsicSize: "0 ${placeholderHeight}px" }}>` (preserves R8c first-paint LCP win + R12 SSR-completeness contract — children always in DOM); after hydration, a `useEffect` schedules a `requestAnimationFrame` callback that flips the style to `{}`, removing content-visibility from every LazyMount. **Subsequent scrolls have no paint-defer, no black voids on fast scroll** — R12's pure CSS implementation skipped paint perpetually, which during fast scroll (10+ wheel-ticks/sec via Magic Mouse / touchpad) lagged behind viewport movement and produced black-void flashes for one or more frames at a time. R13's first-paint-only deferral keeps the LCP benefit (measured at first paint) and the SSR contract (children always in DOM) while eliminating the perpetual paint-defer that caused the flash. `data-lazy-mount` attribute tracks state (`"eager"` / `"lazy"` / `"ready"` — useful for live audit probes). Place the FIRST 2 sections eagerly (they're above the fold; `eager` prop renders normally without containment); wrap sections 3+ with `<LazyMount placeholderHeight={240}>`. **Default `placeholderHeight` reduced from 600 → 240** (R13) — better matches the median first-viewport section height; only applies during the SSR + first-paint window before the RAF flip. `contain-intrinsic-size` reserves layout space before the flip so CLS stays 0. JS-disabled fallback: the SSR-shipped style stays in effect (functional with paint-defer; same UX as R12). Browser support: Chrome / Edge 85+, Safari 18+, Firefox 125+. Older browsers fall back to full eager render (paying layout cost but still seeing content — graceful). **Rule:** never lazy-paint above-the-fold content; always set `placeholderHeight` close to the expected first-viewport section height (default 240 px).

18. **Honor OS modes and print at the system layer — not the component layer** (v0.14 — R9 + R10, ADR 0029). Lumen ships three global media-query blocks in [`audit-dashboard/src/app/globals.css`](audit-dashboard/src/app/globals.css): `@media (prefers-contrast: more)`, `@media (forced-colors: active)`, `@media print`. These re-bind shared `:root` tokens (border-weight upgrades under high-contrast, light-theme forced under print, OS-controlled `CanvasText`/`Highlight` under forced-colors). When generating any new primitive or layout: do NOT hand-author per-component overrides for these OS modes. The system-level blocks cascade through the token system into every primitive automatically. Per-component opt-out is acceptable only when the system block produces a wrong result (e.g., a brand-mark SVG that needs forced-color-adjust: none — that's a brand call documented in the component.md). **Rule:** when adding a new visual primitive, verify under `prefers-contrast: more` + `forced-colors: active` + print preview that the system block produces sane output. If it doesn't, the FIX is in globals.css's media blocks (extend the rebind), not in the component.

19. **Italic content uses `var(--font-satoshi-italic)` family fallthrough; new content authoring rules under i18n scaffold** (v0.14 — R8d + R11 i18n, ADR 0029). After R8d, italic Satoshi lives in a SEPARATE next/font family (`satoshi-italic`) with `display: "optional"` + `preload: false`. The `--font-sans` chain in globals.css includes `var(--font-satoshi-italic)` so `font-style: italic` text falls through the family chain and matches there. Do NOT add manual `@font-face` blocks for italic — the chain works. For i18n / RTL: Lumen primitives use CSS logical properties (`margin-inline-*`, `padding-block-*`) where direction matters. Setting `<html dir="rtl">` flips inline-flow primitives correctly. Directional icons that semantically mean "forward" / "next" (chevrons in breadcrumbs, "advance" arrows) get a `data-rtl-flip` attribute — `[dir="rtl"] [data-rtl-flip] { transform: scaleX(-1); }` is wired in globals.css. Numeric content (prices, counts, percent) gets `data-numeric` which pins LTR direction inside RTL paragraphs (`direction: ltr; unicode-bidi: isolate;`). See [`design-system/00-foundations/internationalization.md`](design-system/00-foundations/internationalization.md). **Rule:** never set `font-family: "Satoshi"` on italic-bearing text — use `var(--font-sans)` and let the chain match; never assume Lumen has been RTL-audited (it has not been visually verified at `dir="rtl"`); use logical properties + the `data-rtl-flip` + `data-numeric` attributes for new direction-sensitive primitives.

20. **No green in any shadow color value — anywhere in the system.** (v0.14 — R11; supersedes the R10 categorical split). The earlier R10 contract carved Lumen shadows into "elevation (neutral)" + "halo/glow (accent)" categories; R11 collapses that into a single rule: **every `box-shadow` color in Lumen is neutral**. The carve-out the system made for "the green focus halo is action, not depth, so it's allowed to be green" was the user's specific objection — green halos around buttons / on focus / under hero CTAs / in command palette / on AI shimmer / on brand-mark hover were all retired. The accent (`color.accent.500 = #00FA8A`) still plays its single role per hard rule 7 — but that role is now scoped to **background fills, border colors, text, leading dots, and atmospheric `background-image: radial-gradient` washes** (the aurora). **NEVER box-shadow.**
    - Replacement defaults: `shadow.focus` → `0 0 0 3px var(--border-frame)` (40 %-alpha theme-aware paper/ink). `shadow.focus.dual.outer` → `var(--border-frame)`. `shadow.accent-glow` → aliases `{shadow.lg}` (neutral elevation). `shadow.button.glow.{rest,active}` → `none`. `shadow.button.glow.hover` → `{shadow.md}`. `shadow.button.ai-shimmer` → `var(--border-frame)` static + `var(--border-strong)` peak. `shadow.input.focus` + `shadow.input.success` → `var(--border-frame)`.
    - Three carve-outs that look like exceptions but aren't: (1) **validation shadows may carry tone color** — `shadow.input.error` (red), `shadow.input.warning` (amber) are validation tones, distinct from action/brand. The mandate is specifically about *green*, not about all colored shadows. (2) **`--aurora-glow-color`** is a `radial-gradient` background, NOT a `box-shadow` — it may keep its lime tint on hero surfaces. (3) **`--surface-tint-accent`, `--border-accent`, `--status-success-bg`, all the pill backgrounds, the LumenMark green core fill** — all are backgrounds or borders, not shadows, and remain green.
    - [`scripts/lint-shadow-no-accent.mjs`](scripts/lint-shadow-no-accent.mjs) enforces R11 at the token-source layer. It walks `01-tokens/primitives/shadow.tokens.json` + `01-tokens/semantic/shadow.tokens.json` and fails CI if ANY shadow token (regardless of name) references `color.alpha.accent.*` / `lumen-accent` / `lumen-lime` / `spring-green` / `00FA8A`. R10's `lint:elevation-no-accent` (which only enforced the rule on the elevation subset) was renamed + broadened.
    - **Rule:** Every new shadow token's color must be neutral (paper-alpha, ink-alpha, shadow-alpha, border-frame, border-strong, or — for validation halos only — `color.alpha.{danger,warning}.*`). Never reach for an accent token in a box-shadow.

## Code style

- TypeScript strict, no `any`.
- React: function components, hooks, no class components.
- Tailwind v4 only — no v3 config files. Theme lives in `_build/tailwind/theme.css` via `@theme`.
- iOS: SwiftUI for new code.
- Android: Jetpack Compose.
- Token references in code: `var(--color-surface-page)`, NOT `#fafaf7`.
- File naming: kebab-case for component folders (`live-dot/`, `empty-state/`); PascalCase for component names in code (`LiveDot`, `EmptyState`).

## Changelog & PR conventions

- Conventional Commits: `feat(button): add loading prop`, `fix(tokens): correct accent.fg contrast`, etc.
- Add a CHANGELOG entry under the matching Keep-a-Changelog category (Added/Changed/Deprecated/Removed/Fixed/Security).
- Token changes: minor or patch decided by deprecation rules below.
- Component changes: minor (new prop) or patch (bug fix).
- Breaking changes: major. Open an ADR.

## Deprecation policy

- Mark tokens deprecated by setting `"$deprecated": "Replaced by {new.token.path} in v0.2.0. Will be removed in v1.0.0."` on the token.
- Mark components deprecated by setting `"deprecated": true` and `"deprecationNotice": "..."` and `"removedIn": "1.0.0"` in `component.json`.
- A deprecation lives ≥ 1 minor release before removal.
- Removal happens in the next major.

## Trust levels (for autonomous agents)

| Level | Action | Examples |
|---|---|---|
| AUTOMERGE | Cosmetic, low-risk | Typo fixes in MD, dead-link fixes, missing alt text on SVGs |
| DRAFT-PR | Reviewable | New components matching the schema, new platform examples, new prompt fragments, token additions (no removals) |
| HUMAN-REVIEW | Always reviewed | Token rename or removal, schema changes, breaking changes to `component.json`, anything that bumps major version, license-affecting changes |

## When in conflict

- User instructions in chat override these rules where they conflict (the user is in control).
- These rules override your training memory of how design systems "usually" work.
- Lint and CI override your assumptions of what's valid.
- The `lumen-brief.md` is the source-of-truth for "why" decisions were made — read it when a rule feels arbitrary.

## What to do if you're stuck

1. Read the relevant `component.md` AND `component.json` together.
2. Check `_meta/decisions/` for an ADR on the topic.
3. Check `_meta/prompts/` for a workflow fragment that matches.
4. Search `research/` for the underlying evidence.
5. If still stuck, surface the question. Do not guess.
