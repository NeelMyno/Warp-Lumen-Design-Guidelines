# ADR 0023 — Lift token contract to DTCG 2025.10

- **Date:** 2026-05-16
- **Status:** Accepted
- **Deciders:** Lumen working group
- **Supersedes (partially):** [ADR 0001 — DTCG JSON format](./0001-dtcg-format.md) (which targeted the DTCG 2024 draft)
- **Related rules:** [AGENTS.md hard rule 17](../../AGENTS.md)

## Context

The DTCG format module 2025.10 stabilized on October 28, 2025 — the first version with full vendor support across Style Dictionary v5, Tokens Studio for Figma, and Specify. Lumen's v0.12.6 token graph was authored against the DTCG 2024 draft (per [ADR 0001](./0001-dtcg-format.md)). The 2024 → 2025.10 deltas affect us in five concrete ways:

1. **Composite type formalization.** `typography`, `shadow`, `gradient`, `transition`, `border` are now first-class composite types with documented sub-token shapes. The 2024 draft permitted ad-hoc objects under `$value`; 2025.10 mandates a structured sub-object per composite type.
2. **OKLCH support promoted from extension to first-class color space.** The 2024 draft allowed OKLCH only via `$extensions`; 2025.10 makes OKLCH a recognized `$type: "color"` value form. Lumen's primitives can now ship OKLCH directly without extension wrapping.
3. **Alias resolution semantics tightened.** 2025.10 specifies that `{token.path}` aliases MUST resolve to a single declared token in the same JOIN graph; partial-path aliasing is invalid. Lumen's pre-2025.10 build silently allowed some partial aliases that 2025.10 SD v5 flags as errors.
4. **`$schema` URL updated.** The canonical schema URL is `https://www.designtokens.org/schemas/2025.10/format.json`. Every Lumen `.tokens.json` file's top-level `$schema` field must reference this URL.
5. **Dimension object form mandated.** 2025.10 requires `{value: 8, unit: "px"}` for dimension tokens (vs. the 2024 draft's permissiveness for bare numbers). Lumen's `dimension.tokens.json` was already authored in this shape; 2025.10 makes it required.

This ADR documents the lift performed in Phase 0 of the v0.13.0 refactor (commit `f043515`).

## Decision

**Lift every Lumen `.tokens.json` file's `$schema` field to `https://www.designtokens.org/schemas/2025.10/format.json`. Adopt the 2025.10 composite-type sub-shapes verbatim. Keep OKLCH values in `$extensions.lumen.oklch` rather than as the primitive `$value` to preserve string-comparison parity with the foundations page's hex values. Pin Style Dictionary at `^5.0.0` for the 2025.10 transform set.**

The decision is additive — every v0.12.6 token name and value is preserved verbatim. Aliases and composite shapes are updated in place; no token is renamed; no token is removed.

### Specific commitments

- Every `$value` carries an explicit `$type` (one of the 13 DTCG types).
- Every leaf token has a `$description` string (no anonymous tokens).
- Aliases use the `{token.path.name}` syntax exclusively. No `var(--css-name)` references in the source.
- Composite types (`typography`, `shadow`, `gradient`) ship their full sub-object shape per the 2025.10 spec. Multi-layer shadows are arrays of the composite shape, not concatenated CSS strings.
- Hex values remain the canonical `$value` for color primitives; OKLCH lives in `$extensions.lumen.oklch` for the Style Dictionary OKLCH transform consumer.

## Consequences

### Positive

- **Toolchain parity.** Style Dictionary v5, Tokens Studio 2026.04+, and Specify all consume Lumen tokens out of the box. No fork, no shim.
- **Better LLM retrieval.** The `$description` field on every leaf gives an AI agent a one-line context block per token without parsing surrounding documentation.
- **Composite tokens emit reliably.** The composite-shape constraint lets the SD v5 transforms (`size/composite`, `shadow/composite`) emit consistent CSS / Swift / Compose output.
- **Schema reference is canonical.** `https://www.designtokens.org/schemas/2025.10/format.json` is stable; LLMs and JSON validators can fetch it directly.

### Negative

- **Style Dictionary v5 dependency.** SD v4 cannot consume 2025.10 composite types correctly. Lumen pins SD `^5.0.0` and downstream consumers must use SD v5 if they author their own tokens against the Lumen graph.
- **Migration discipline required.** Every new `.tokens.json` file in the repo must declare `$schema: "https://www.designtokens.org/schemas/2025.10/format.json"`. Drift will produce confusing validation errors. `scripts/validate-tokens.mjs` enforces this.
- **OKLCH-as-extension vs. OKLCH-as-primitive trade-off.** Other v0.13 design systems (Vercel Geist v3) made OKLCH the primary `$value`. Lumen kept hex primary to preserve string parity with the foundations page. The cost: an extra hop through `$extensions.lumen.oklch` when downstream consumers want OKLCH.

### Risks

- **2025.10 may still see point revisions before 1.0.** The DTCG working group reserved the right to issue 2025.11+ patch versions before a 1.0 lock. Lumen pins `2025.10` literally; if 2025.11 ships breaking changes, we re-evaluate.
- **Some 2024-era third-party tools may not read 2025.10 cleanly.** Audit: only Tokens Studio for Figma v2025.04+ guarantees compatibility. Older Tokens Studio versions will misread composite shadows.

## Alternatives considered

### A. Stay on DTCG 2024 draft for v0.13, lift in v0.14

Rejected. The 2024 draft is end-of-life as of 2025.10's stabilization. Staying would mean shipping v0.13.0 with a deprecated schema and re-lifting in v0.14 anyway — net negative on stability narrative.

### B. Author tokens in custom JSON, generate DTCG on build

Rejected. Adds a translation layer between author and consumer; LLMs would have to learn two formats. The DTCG-authored source is itself the SSOT; the build pipeline emits platform-specific outputs from it.

### C. Wait for DTCG 1.0 stable

Rejected. The DTCG working group has not committed to a 1.0 timeline. The 2025.10 spec is the closest thing to "1.0 in spirit." Waiting indefinitely means leaving the ecosystem fragmented.
