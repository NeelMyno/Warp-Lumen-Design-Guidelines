# examples/gpt-image-2

Reference assets for the Lumen [`05-prompts/`](../../design-system/05-prompts/) library. One canonical PNG per template (five for `mesh/`) generated at the snapshot-pinned model `gpt-image-2-2026-04-21`. These are the **visual baseline** the team diffs against when re-baselining (the gpt-image-2 alias rolls forward, the snapshot pin lifts, or a template gets a subject edit).

---

## What ships here vs. what an operator materializes

| File | Status | Provenance |
|---|---|---|
| `<template>/canonical-subject.md` | ✓ in repo | Declarative manifest — the exact subject string the canonical PNG is generated from. |
| `<template>/<slug>.png` | ◐ **operator-materializes** | Generated by `pnpm prompts:generate-references` against `gpt-image-2-2026-04-21` with `OPENAI_API_KEY` set. |
| `mesh/aurora-spring.png` … `mesh/cross-dock.png` | ◐ **operator-materializes** | Five PNGs generated as a single thinking-mode session for cross-recipe consistency. |

The PNGs are **not committed to git in the Phase 4 ship**. Two reasons:

1. **No CI key.** This repo's CI does not carry an `OPENAI_API_KEY`. Reference generation is interactive and budgeted — the operator runs it locally, reviews the visual output, and commits the PNGs in a follow-up dedicated PR.
2. **Snapshot pin may not resolve at run time.** `gpt-image-2-2026-04-21` is the contracted snapshot per master doc §11. Per the master doc itself, the alias may roll forward; the operator re-baselines when it does. Auto-generation in CI would silently consume whatever snapshot OpenAI serves on the day, which is the drift signal we explicitly guard against.

## How to materialize the references (operator-side)

```bash
# 1. Set your OpenAI key
export OPENAI_API_KEY="sk-…"

# 2. Run the generator
pnpm prompts:generate-references

# 3. Review every PNG visually before committing — the mesh set especially
#    must be cross-recipe consistent (use the same thinking-mode session).

# 4. Commit the PNGs in a dedicated PR titled
#    "examples(gpt-image-2): regenerate against snapshot YYYY-MM-DD"
```

The generator reads each `<template>/canonical-subject.md` for the canonical subject text, calls the CLI internally to assemble the full prompt, and POSTs to OpenAI's `/v1/images/generations` endpoint. See [`tools/lumen-prompts/generate-references.ts`](../../tools/lumen-prompts/generate-references.ts).

---

## When to regenerate

Regenerate the full reference set when any of the following happens:

| Trigger | Action |
|---|---|
| `gpt-image-2-2026-04-21` snapshot is deprecated or replaced | Update the pin in master doc §9, `05-prompts/style-anchor.md`, every template, then regenerate ALL references in one PR. |
| Style anchor body changes (extremely rare — see `style-anchor.md` warning) | Bump to `style-anchor.v2.md`, migrate consumers, regenerate ALL references. |
| A template's canonical subject changes | Regenerate only that template's references; commit alongside the subject edit. |
| Visual drift detected (a template's output looks materially different from the prior PNG even with the same subject + snapshot) | File a drift incident; document in the next phase report. |

---

## Diff-against-baseline

When regenerating, the diff against the prior PNG is the **drift signal**. Three failure modes the diff catches:

1. **Snapshot rolled forward without re-baseline** — output differs visibly even though subject + pin string are unchanged. Open an issue, decide whether to lift the pin or roll back.
2. **Subject edit had unintended ripple** — output differs MORE than the edited subject would predict. Re-read the prompt assembly to confirm slot resolution.
3. **Anchor change leaked through** — if the anchor was edited (it should NEVER be), every template's reference will drift simultaneously. Hard-revert the anchor change.
